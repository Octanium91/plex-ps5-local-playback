# Plex на PlayStation 5 Pro — локальне відтворення без підписки

Медіасервер стоїть у сусідній кімнаті, консоль — у тій самій мережі, а Plex усе одно вимагає платити
за «віддалений» перегляд. Це повний шлях до локальної роботи: що робити, як перевірити кожен крок і —
що не менш важливо — **на що не варто витрачати час**.

Перевірено на **PlayStation 5 Pro**, застосунок Plex `1.007.001`, Plex Media Server `1.43.4.10903`
(`lscr.io/linuxserver/plex`, `network_mode: host`) на Debian 13, вересень 2026 року.

Той самий шлях працює для будь-якого клієнта з мінімальним TLS-стеком — Xbox, Roku, старіші
Android TV, LG webOS поводяться тут однаково.

> **Найперше оновіть Plex Media Server.** Цей посібник описує поведінку сервера станом на вересень
> 2026 року. Якщо Plex відтоді змінив спосіб побудови ланцюжка сертифікатів, звичайне оновлення і є
> повним розв'язанням.

## Почніть звідси: знайдіть свій симптом

Найімовірніше, ви прийшли сюди з чимось конкретним на екрані. Знайдіть це нижче.

| Що ви бачите | Що це означає | Куди йти |
|---|---|---|
| **«Remote Playback requires a Remote Watch Pass»** — у власній домашній мережі | Консоль так і не встановила локальне з'єднання та перейшла на віддалене | [§1 — почніть з цього](#1-почніть-з-цього) |
| Сервер у списку є, але позначений як **Віддалений** | Та сама причина | [§1](#1-почніть-з-цього) |
| **Працює в браузері й на телефоні, не працює лише на консолі** | Класична ознака саме цієї ситуації | [§1](#1-почніть-з-цього), далі [§3 — чому](#3-чому-так-стається) |
| `tlsv1 alert unknown ca` у журналі сервера | Консоль відхилила сертифікат сервера — ланцюжок неповний | [§2 — переконайтеся](#2-переконайтеся-що-ви-за-адресою) |
| `CERT: incomplete TLS handshake from <адреса-консолі>` | Той самий рядок, та сама причина | [§2](#2-переконайтеся-що-ви-за-адресою) |
| Консоль **узагалі не бачить сервер** | Може бути й інша причина — спершу перевірте ланцюжок | [§2](#2-переконайтеся-що-ви-за-адресою) |
| Ви вже змінили DNS на консолі, і нічого не сталося | Так і мало бути — DNS тут ні до чого | [§4 — що не працює](#4-чого-робити-не-варто) |
| Ви вже налаштували власний сертифікат, а бар'єр лишився | Теж очікувано, і це закладено в архітектуру | [§4](#4-чого-робити-не-варто) |
| Раніше працювало й зламалося саме по собі | Ротація сертифіката — той самий шлях | [§8](#8-після-ротації-сертифіката) |
| Ви видалили сертифікат, і тепер сервер узагалі без нього | Ви досягли ліміту — відновіть резервну копію | [§5](#5-єдине-що-справді-може-нашкодити) |

Якщо коротко: **проблема з ланцюжком сертифікатів виглядає як проблема з оплатою.** Саме через цей
розрив її так важко знайти в пошуку.

## 1. Почніть з цього

Plex зберігає свій сертифікат `plex.direct` у кеші на диску. Якщо його видалити, сервер замовить
новий — цього разу з повним ланцюжком.

**Де лежить кеш:**

| Установлення | Шлях |
|---|---|
| Docker (`linuxserver/plex`) — на хості | `<ваш-том>/Library/Application Support/Plex Media Server/Cache/` |
| Docker — усередині контейнера | `/config/Library/Application Support/Plex Media Server/Cache/` |
| Linux (нативний пакет) | `/var/lib/plexmediaserver/Library/Application Support/Plex Media Server/Cache/` |
| macOS | `~/Library/Caches/PlexMediaServer/` |
| Windows | `%LOCALAPPDATA%\Plex Media Server\Cache\` |

У поточних версіях файл називається `cert-v2.p12`, у старіших — `certificate.p12`. Видаліть той, що
є, і **спершу зробіть резервну копію** — вона знадобиться, якщо щось піде не так.

```bash
CACHE="./config/plex/Library/Application Support/Plex Media Server/Cache"

docker compose stop plex

# резервна копія того, що є
for f in cert-v2.p12 certificate.p12; do
  [ -f "$CACHE/$f" ] && cp -a "$CACHE/$f" "$CACHE/$f.bak"
done

rm -f "$CACHE/cert-v2.p12" "$CACHE/certificate.p12"
docker compose up -d plex
```

> **Виконайте це один раз.** Кожне видалення запускає перевипуск, а повторення впирається в ліміт
> Let's Encrypt, після чого ви залишитеся взагалі без сертифіката. Перш ніж пробувати вдруге,
> прочитайте [§5](#5-єдине-що-справді-може-нашкодити).

Далі відкрийте Plex на консолі. Якщо застосунок пам'ятає попередній стан — вийдіть з облікового
запису та увійдіть знову через `plex.tv/link`.

Перевірте результат за [§6](#6-перевірка-результату), перш ніж вважати, що все спрацювало.

## 2. Переконайтеся, що ви за адресою

Ознаки:

- Консоль показує сервер як недоступний або підключається, але позначає його як **Віддалений**
- Відтворення блокує напис **«Remote Playback requires a Remote Watch Pass»** — у власній мережі
- **Усі інші клієнти працюють**: браузер, телефон, комп'ютер
- У журналі сервера раз по раз з'являється:

```
CERT: incomplete TLS handshake from 192.168.1.50:62749: tlsv1 alert unknown ca (SSL routines)
```

### Дізнайтеся своє ім'я plex.direct

У кожного сервера власний 32-символьний хеш. Запитайте про нього сам сервер:

```bash
openssl s_client -connect <адреса-сервера>:32400 </dev/null 2>/dev/null \
  | openssl x509 -noout -subject
# subject=CN=*.01c00d0663104e03b8de1fa2a2b4baf5.plex.direct
#             ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ це ваш хеш
```

Локальне ім'я — це адреса сервера в мережі з дефісами замість крапок плюс цей хеш:
`192-168-1-100.<хеш>.plex.direct`

### Подивіться на ланцюжок

```bash
HASH=01c00d0663104e03b8de1fa2a2b4baf5      # ваш, з попередньої команди
IP_DASHED=192-168-1-100                     # локальна адреса сервера з дефісами

openssl s_client -connect <адреса-сервера>:32400 \
  -servername $IP_DASHED.$HASH.plex.direct -showcerts </dev/null 2>/dev/null \
  | grep -E '^ [0-9] s:|^   i:'
```

**Два сертифікати — посібник саме про вас:**

```
 0 s:CN=*.<хеш>.plex.direct
   i:C=US, O=Let's Encrypt, CN=YR2
 1 s:C=US, O=Let's Encrypt, CN=YR2
   i:C=US, O=ISRG, CN=Root YR
```

Ланцюжок обривається на `Root YR`, якому сам собою не довіряє жоден клієнт.

**Три сертифікати, останній виданий `ISRG Root X1` — ланцюжок у вас уже правильний**, і причина
негаразду інша.

Проміжний сертифікат може бути `YR1`, `YR2` чи `YR3` (або з родини `YE*` для ключів ECDSA) — важливо
не те, який саме підписав кінцевий, а те, **чим ланцюжок завершується**.

## 3. Чому так стається

**13 травня 2026 року** Let's Encrypt перевів типовий профіль видачі на
[ієрархію Generation Y](https://letsencrypt.org/2025/11/24/gen-y-hierarchy.html). Сертифікати для
`*.plex.direct` Plex отримує за ваш сервер: Plex Media Server генерує ключ і надсилає запит на
підпис (CSR) до plex.tv, а plex.tv бере сертифікат у центру сертифікації та повертає серверу. Тому
сервери почали автоматично отримувати сертифікати з нової ієрархії.

Нових кореневих сертифікатів — **ISRG Root YR** та **ISRG Root YE** — поки немає в жодному сховищі
довіри; Let's Encrypt пише про це прямо на сторінці
[Chains of Trust](https://letsencrypt.org/certificates/). Сумісність забезпечує **перехресний
підпис**: `ISRG Root YR` додатково підписаний давно довіреним `ISRG Root X1`.

Тому повний ланцюжок має виглядати так:

```
кінцевий сертифікат (*.<хеш>.plex.direct)
  └── Let's Encrypt YR2
        └── ISRG Root YR   (перехресно підписаний ISRG Root X1)   ← сервер має надіслати і це
              └── ISRG Root X1   (є в кожному сховищі довіри)
```

Коли надсилаються лише перші дві ланки, клієнтові немає до чого прив'язати шлях довіри.

### Чому страждають саме консолі та телевізори

Windows, macOS та iOS виконують **AIA chasing** — якщо ланки бракує, вони дозавантажують її
самостійно за посиланням у розширенні Authority Information Access. Мінімальні TLS-стеки консолей і
смарт-телевізорів так не вміють: вони очікують повний ланцюжок від сервера й завершують з'єднання
помилкою `unknown ca`.

Системний TrustManager в Android теж не робить AIA chasing — мобільні застосунки Plex, найімовірніше,
несуть власні якорі довіри, і саме тому продовжують працювати. Так чи інакше, у консолі такого
запасного виходу немає.

Саме тому браузер на комп'ютері працює, а PS5 Pro за три метри — ні.

### Чому це виглядає як вимога підписки

Ланцюжок наслідків — те, що найбільше заплутує під час діагностики:

1. Консоль не може завершити TLS до **локальної** адреси → придатного локального з'єднання немає
2. Вона переходить на **віддалене** з'єднання, опубліковане на plex.tv
3. Віддалене відтворення на консолях потребує платної підписки → з'являється платний бар'єр

**Підписка — остання ланка ланцюжка, а не причина.** Боротьба з нею напряму нічого не дає — див.
наступний розділ.

## 4. Чого робити не варто

Усе наведене нижче було справді випробувано й виміряно під час цього розслідування. Жодне не
допомагає. Список наведено, щоб ви не витратили цілий вечір.

| Спроба | Що відбувається насправді |
|---|---|
| Змінити DNS на консолі на `8.8.8.8` / `1.1.1.1` | Нічого не змінюється. Маршрутизатор і так перетворює `plex.direct` на приватну адресу — перевірте через `nslookup`, перш ніж вірити зворотному. |
| Вимкнути DNS Rebinding Protection на маршрутизаторі | Не причина. `unknown ca` виникає **після** того, як DNS і TCP вже спрацювали. |
| Поставити `secureConnections` у Disabled | PS5 Pro жодного разу не пробує HTTP. Підтверджено через `tcpdump`: 24 спроби TLS, нуль HTTP. |
| Шукати «Allow insecure connections» у застосунку консолі | У версії `1.007.001` такого параметра немає — там узагалі відсутній розділ мережі. |
| `customConnections` (Custom server access URLs) | У PMS 1.43.4 мовчки ігнорується — значення зберігається, але на plex.tv не публікується. |
| Власний сертифікат через `customCertificateDomain` | TLS проходить, консоль підключається, але з'єднання завжди має позначку `local=false`, тож бар'єр залишається. |
| Спрямувати A-запис цього домену на приватну адресу | Позначка не змінюється. |
| Піддомен у вигляді адреси з дефісами (`192-168-1-100.example.com`) | plex.tv його не розбирає. Однаково `local=false`. |
| Вимкнути Relay, віддалений доступ чи ручне перенаправлення порту | Прибирає віддалене з'єднання разом з єдиним, яке консоль здатна встановити. |
| Видалити консоль з облікового запису, перевстановити застосунок | Не змінює нічого — позначка обчислюється щоразу під час запуску сервера, а не кешується. |
| Транслювати на PS5 Pro через DLNA | Вона **не є** DLNA-рендерером. Її відповіді SSDP на порту 40001 належать Remote Play та Second Screen. |
| Шукати застосунок «Media Player» у PS Store | Для PS5 його не існує — це був застосунок для PS4. Media Gallery відтворює лише з USB. |

### Чому шлях із власним сертифікатом не спрацює ніколи

Варто розуміти, бо саме він здається очевидним рішенням.

PMS **не надсилає** позначку `local`. Він публікує звичайний перелік адрес:

```
PUT https://servers.plex.tv/devices/{machineIdentifier}
    ?Connection[][uri]=http://192.168.1.100:32400
    &Connection[][uri]=http://172.17.0.1:32400
    &httpsEnabled=1&httpsRequired=0&dnsRebindingProtection=0
```

Класифікацію робить **бекенд** plex.tv, розбираючи хост кожної адреси:

| Що надсилає PMS | Висновок plex.tv |
|---|---|
| Приватна адреса RFC1918 (`192.168.x`, `10.x`, `172.16–31.x`) | `local=1`, генерує `https://<адреса-з-дефісами>.<хеш>.plex.direct:порт` |
| Публічна адреса | `local=0`, теж генерує ім'я plex.direct |
| CGNAT `100.64.0.0/10` (Tailscale) | відкидається повністю — не з'являється в `/api/v2/resources` |
| **Будь-яке доменне ім'я** | `local=0`, ім'я plex.direct не генерується |

Жодного перетворення DNS не відбувається. Домен не є числовою адресою, тож локальним він не стане
ніколи — байдуже, куди вказує та як записаний. Параметра в Preferences.xml, який це змінює, не
існує; `LanNetworksBandwidth` впливає лише на серверний облік пропускної здатності.

Отримати власний сертифікат для `plex.direct` теж не вийде. Його запис CAA має такий вигляд:

```
0 issue ";"
0 issuewild "letsencrypt.org"
0 issuewild "digicert.com"
```

Звичайна видача заборонена всім центрам сертифікації, а видача wildcard дозволена лише двом — і
жоден із них не видасть сертифікат вам, бо підтвердження контролю над доменом потребує доступу до
DNS-зони Plex.

## 5. Єдине, що справді може нашкодити

Кожне видалення сертифіката запускає його перевипуск. Повторіть кілька разів — і отримаєте
**HTTP 429**, після чого сервер залишиться **взагалі без сертифіката**. Ліміт належить центру
сертифікації: Plex може скинути власні лічильники, але не лічильники ЦС. Судячи з обговорень на
форумі Plex, чекати доводиться приблизно тиждень. Люди вже ламали собі TLS у такий спосіб під час
налагодження.

**Видаліть один раз. Якщо не допомогло — переходьте до [§7](#7-якщо-швидке-рішення-не-допомогло), а
не повторюйте.**

### Якщо сертифіката вже немає

Поверніть на місце резервну копію з §1:

```bash
CACHE="./config/plex/Library/Application Support/Plex Media Server/Cache"

docker compose stop plex
cp -a "$CACHE/cert-v2.p12.bak" "$CACHE/cert-v2.p12"    # або certificate.p12.bak
docker compose up -d plex
```

Це поверне **старий, неповний** ланцюжок — консоль так і не працюватиме, зате сервер лишиться
придатним для всіх інших клієнтів, поки ви чекаєте закінчення ліміту.

Для Docker: переконайтеся, що `Cache/` лежить на **постійному томі**. Якщо том тимчасовий,
сертифікат знищується під час кожного перезапуску контейнера, і рано чи пізно ліміт неминучий.

## 6. Перевірка результату

**Ланцюжок** — тепер три сертифікати, останній виданий ISRG Root X1:

```
 0 s:CN=*.<хеш>.plex.direct
   i:C=US, O=Let's Encrypt, CN=YR2
 1 s:C=US, O=Let's Encrypt, CN=YR2
   i:C=US, O=ISRG, CN=Root YR
 2 s:C=US, O=ISRG, CN=Root YR
   i:C=US, O=Internet Security Research Group, CN=ISRG Root X1     ← перехресний підпис
```

**Вирішальна перевірка** — валідація *лише* кореневим ISRG Root X1, тобто тим, що є в консолі:

```bash
openssl s_client -connect <адреса-сервера>:32400 \
  -servername $IP_DASHED.$HASH.plex.direct \
  -CAfile /etc/ssl/certs/ISRG_Root_X1.pem </dev/null 2>/dev/null \
  | grep "Verify return code"
# очікуємо: Verify return code: 0 (ok)
```

**Консоль перестала падати** — лічильник має лишатися нульовим:

```bash
grep -c 'incomplete TLS handshake from <адреса-консолі>' \
  "<config>/Library/Application Support/Plex Media Server/Logs/Plex Media Server.log"
```

**Відтворення справді локальне** — запустіть фільм і подивіться на сеанс:

```bash
curl -s -H "X-Plex-Token: <токен>" "http://<адреса-сервера>:32400/status/sessions" \
  | grep -oE 'local="[01]"'
# очікуємо: local="1"
```

## 7. Якщо швидке рішення не допомогло

На деяких серверах перевипуск усе одно дає скорочений ланцюжок. Тоді його можна полагодити вручну:
дістати сертифікат і ключ, дописати перехресний підпис і зібрати файл наново. Пароль до p12
обчислюється детерміновано з ідентифікатора машини.

```bash
umask 077        # зараз приватний ключ буде записано у відкритому вигляді

P="<config>/Library/Application Support/Plex Media Server"
MID=$(sed -n 's/.*ProcessedMachineIdentifier="\([^"]*\)".*/\1/p' "$P/Preferences.xml")
PASS=$(printf '%s' "plex${MID}" | openssl dgst -sha512 | cut -d' ' -f2)   # саме printf, не echo

openssl pkcs12 -in "$P/Cache/cert-v2.p12" -passin "pass:$PASS" -nodes -nocerts -out key.pem
openssl pkcs12 -in "$P/Cache/cert-v2.p12" -passin "pass:$PASS" -nodes -nokeys  -out leafchain.pem

curl -fsSLO https://letsencrypt.org/certs/gen-y/root-yr-by-x1.pem

# leafchain.pem уже містить кінцевий і проміжний; -certfile додає ЛИШЕ відсутній перехресний підпис
openssl pkcs12 -export -out fixed.p12 -in leafchain.pem -inkey key.pem \
  -certfile root-yr-by-x1.pem -passout "pass:$PASS" \
  -certpbe AES-256-CBC -keypbe AES-256-CBC -macalg SHA256
```

Переконайтеся, що вийшло рівно три сертифікати, а не п'ять:

```bash
openssl pkcs12 -in fixed.p12 -passin "pass:$PASS" -nokeys -info 2>/dev/null \
  | grep -c "BEGIN CERTIFICATE"
# очікуємо: 3
```

Тепер установіть його:

```bash
docker compose stop plex
cp -a "$P/Cache/cert-v2.p12" "$P/Cache/cert-v2.p12.bak"
cp fixed.p12 "$P/Cache/cert-v2.p12"
chown 1000:1000 "$P/Cache/cert-v2.p12"      # відповідно до PUID/PGID вашого контейнера
chmod 600 "$P/Cache/cert-v2.p12"
docker compose up -d plex

shred -u key.pem 2>/dev/null || rm -f key.pem
```

Перевірте результат за [§6](#6-перевірка-результату).

Примітки:

- На **OpenSSL 1.1.1 і старіших** прапорці `-certpbe / -keypbe / -macalg` обов'язкові — без них PMS
  не прочитає файл. В OpenSSL 3.x це вже типові значення, але залишити їх не завадить.
- Під час ротації (приблизно раз на 90 днів) PMS **перезапише цей файл**, тож знадобиться таймер.
  Див. [§8](#8-після-ротації-сертифіката).

Варто також повідомити Plex: з їхнього боку виправлення полягає в тому, щоб додавати
`root-yr-by-x1.pem` до ланцюжка, і це закрило б питання для всіх пристроїв одразу.

## 8. Після ротації сертифіката

Кінцевий сертифікат `plex.direct` оновлюється автоматично приблизно раз на 90 днів. Якщо до того часу
Plex не змінить поведінку, скорочений ланцюжок може повернутися. Ознака — той самий рядок у журналі:

```
CERT: incomplete TLS handshake from <адреса-консолі>: tlsv1 alert unknown ca
```

Перевірте ланцюжок командою з [§2](#2-переконайтеся-що-ви-за-адресою) — і пам'ятайте про ліміт,
перш ніж щось видаляти.
